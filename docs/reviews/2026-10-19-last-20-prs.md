# Review of the latest 20 merged PRs

Reviewed `37c83f8c..2962276e` on 19 October 2026: the latest 20 merges into
`master` when the review began. The review examined each merge's changes and the
integrated implementation, including callers, persistence boundaries, existing
tests, and browser navigation. This is a source review with regression checks,
not a claim that every possible player path was exercised.

An independent subagent critiqued the candidate findings before implementation.
It confirmed the findings below, refined the Escape reproduction, and
rejected the suspected historical-run and manual-history regressions.

## Confirmed findings and root cause fixes

### 1. P2: Following the target was absent from long-range forecasts (#564)

New public games follow the inflating target at live month rollovers. Long-range
forecasts call `generateNewTimeline`, which does not execute those rollovers and
instead billed every future month at today's nominal rate. This understated
future revenue and distorted the cash chart and runway warnings. Turning following
off at the same current price also retained the old cached projection because
`projectionSignature` omitted the setting.

The fix resolves future-month base prices with the same eligible target calculation
used by live play, before applying customer-program billing adjustments. Both the
demand and financial passes use it. The current month's actual rate remains the
source of truth, and an explicit manual-rate probe disables following in its
private copy. The projection signature now includes the setting.

Regression evidence: hourly following/fixed forecasts agree through the opening
month, then bill different rates and cash after January; the expected future bill
comes from the existing target helper. A same-price toggle changes the cache key.
Manual probes preserve their proposed price and do not mutate the live game.
The forecast and cache regressions failed against the original implementation.

### 2. P2: Escape discarded program drafts behind the app menu (#554/#559)

With a program decision open, opening the app menu and pressing Escape ran the
program's document capture listener before the foreground MUI Menu could consume
the key. The program detail closed, its unsaved selection disappeared, and its
clock pause was released while the menu stayed open.

The fix lets the program handle Escape during bubbling. Foreground menus and
dialogs keep their existing event ownership; a subsequent Escape in the decision
returns to its overview. This avoids maintaining another list of overlay types.

Regression evidence: a test using the real app menu checks that the first Escape
closes only the menu while retaining the draft's tier, daily window, and pause;
the next Escape leaves the decision. The test fails with the original capture
listener. A browser regression covers the same interaction on desktop and phone.

### 3. P2: Bundle retries could inspect the wrong build (#562/#573)

`check:ci` leaves the desktop renderer in the shared `build/` directory. Selecting
only the bundle gate reused that artifact, or any stale web build, against the web
bundle ceilings. A full check also ran the bundle gate after a failed web build.

The fix declares the production build as the bundle gate's dependency, using the
check runner's existing selection and failure propagation. Selecting `bundle`
now builds web first, and a failed build skips bundle inspection.

Regression evidence: the selection and failure-propagation tests both failed
before adding the dependency and pass afterward.

### 4. P3: Imported saves accepted a non-boolean following flag (#564)

`parseSave` did not validate the new optional `rateFollowsTarget` field. An edited
save containing the string `"false"` was accepted and treated as enabled at the
next rollover.

The fix rejects present non-boolean values at the existing save boundary. True,
false, and omission remain accepted for the optional setting.
Regression tests cover those cases and malformed strings, numbers, null, and
objects; the malformed cases failed before the validation was added.

### 5. P3: CI diagnostics generated commands that selected no tests (#562)

The diagnostics helper routed all browser failures through the restricted
`test:e2e:ci` configuration. Specs outside its allowlist could not run, and
failures without a named project produced `--project=undefined`.

The fix uses the general `test:e2e` runner for focused reproductions and adds the
project argument only when present. The existing multiplayer and native-window
routes remain intact. The general runner starts development by default; use the
documented `E2E_BASE_URL` option when a reproduction needs a hosted production
build. Tests cover named and unnamed projects and a spec outside the CI allowlist.

### 6. P3: A chart browser test pointed outside the final sample (pre-existing)

The integrated browser matrix exposed an additional failure in the imported-power
blackout test. The first qualifying shortage was point 95 of 96, and the test mapped
it to `bounds.x + bounds.width`, exactly outside the plot's right edge. The tooltip
remained empty. The subagent confirmed the endpoint and pointer position from the
failure trace; no chart-runtime defect was demonstrated. Git blame confirms that
the faulty coordinate calculation predates these 20 PRs. It is included as an
additional validation finding, not attributed to a recent PR.

The test now selects the identified sample through the chart's supported keyboard
controls, preserving both the imported-power and blackout assertions. This tests
the data at the actual point without relying on pixel hit-testing at an excluded
boundary. Other cases continue to cover mouse hover.

## Concerns considered and rejected

- Manual browser-history synchronization predates these PRs. The added manual
  trail follows the existing navigation model; no distinct new failure was
  established that warrants changing global history behavior here.
- The workspace deliberately unmounts hidden decision tools to release their
  clock pauses, retaining preferences in workspace memory. The Steam checkpoint
  optimization requires acknowledgements from the current connection, invalidates
  receipts when a different save is queued, and retries failed peers. No additional
  concrete defect was established in those paths.
