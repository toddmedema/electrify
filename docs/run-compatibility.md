# Challenge compatibility

Friend challenges name a scenario, seed and difficulty. We deploy several times a day,
so a challenge link, like a saved run, is carried forward to the rules of whichever
build opens it (`carryInvitationForward` and `carryRunForward` in
`src/helpers/RunIdentity.ts`): both players face the same scenario, seed and
difficulty, though not necessarily the same build. `src/data/RunCompatibility.json` records a SHA-256 content
identity, generated by `npm run compatibility:generate`. The manifest is a build
artifact: it is git-ignored, and the npm pre-hooks of start, build, test, sim and
typecheck regenerate it, so every build derives it from its own sources. It is
never committed, which keeps concurrent branches from conflicting on it.

The generator hashes the explicit rules revision, relative filenames and content
digests of:

- Simulation data, helpers and reducers under `src/data`, `src/helpers` and
  `src/reducers`, excluding tests and the generated manifest itself.
- Shared constants, domain types and the exact dependency lockfile.
- All shipped weather binaries, data indexes and economic/fuel CSVs under
  `public/data`.

Text line endings are normalized to LF; binary bytes are hashed unchanged. Files
are sorted by path. An input that is only a Git LFS pointer is rejected.

This deliberately broad set changes after harmless helper or type edits. It no longer
gates challenges, saves or replays; it identifies the exact rules a run was captured
under. Replays detect drift from the original run with recorded month-end checkpoints
instead (see `replayDiverged` in `src/Replay.tsx`). It avoids maintaining a fragile
duplicate list of individual simulation formulas. Because inputs are selected by directory, keep content that
only the interface reads, such as manual entries or map artwork, under
`src/components` rather than `src/data`, so editing it does not invalidate
challenges. No historical simulation runtime is provided. Saved games, including
challenged runs in progress, carry forward silently, as described in
[save upgrades](save-upgrades.md).

When changing simulation behavior outside these directories, add the source to
the generator's inputs, or bump `rulesRevision` in the generator.
Changes to the digest algorithm or input-selection policy also require a rules
revision bump. Authored references carry the scenario, seed, difficulty and this
single compatibility digest. Only the current challenge reference and invitation
shapes are accepted; a digest from another build is replaced, not rejected.

The manifest also includes per-file fetch integrity metadata. Browser CSV and
weather loads verify the actual response bytes, including offline-cache responses,
against the build's expected SHA-256. A mismatched response uses the existing
loading-error path instead of initializing a falsely equivalent run. Shipped text
data must use LF line endings, as enforced by `.gitattributes`; the generator
rejects CRLF data so integrity metadata remains portable across build platforms.

The manifest represents the data shipped with this build. Deployment must publish
application code and its matching `public/data` together; it must not replace
simulation data independently under an already-published build.
