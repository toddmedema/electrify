# Challenge compatibility

Friend challenges name a scenario, seed, difficulty and the current simulation rules.
Challenge comparisons require matching rules; saved progress, leaderboard eligibility and
scenario-completion credit continue across updates through the [save loader](saves.md).
`src/data/RunCompatibility.json` records SHA-256 runtime identities, generated by
`npm run compatibility:generate`. The manifest is git-ignored; the npm pre-hooks of
start, build, test, sim and typecheck regenerate it from the current sources.

The official-run `compatibilityId` hashes the explicit rules revision, relative filenames
and normalized executable content of the game reducer and its runtime dependencies:

- Start at `src/reducers/Game.tsx` and follow imports, re-exports, literal `require` calls
  and literal dynamic imports, including dependencies introduced outside the usual simulation
  directories. Unresolved or computed dependencies fail generation instead of being skipped.
- Erase TypeScript types and comments and normalize formatting and string quote choice before
  hashing. Type-only imports and unrelated helpers or reducers do not enter this graph.
- Include installed package versions and integrity digests for imported runtime packages and
  their transitive, optional and installed peer dependencies. Changes to unrelated development
  tools or UI packages do not split official runs.
- All shipped weather binaries, data indexes and economic/fuel CSVs under
  `public/data`.

Text line endings are normalized to LF; binary bytes are hashed unchanged. Files
are sorted by path. An input that is only a Git LFS pointer is rejected.

There are two audited presentation boundaries: `TutorialPrompt.tsx` and
`CustomerGrowthChallenge.tsx` under `src/components/base`. Scenarios hold these React
components for rendering instructions; their implementations do not change simulation state.
Their importing modules, including authored JSX, tutorial conditions and import paths, remain
covered. Other new components or dependencies are included automatically.

This removes common false changes while remaining conservative about executable edits.
Refactoring a runtime formula can still change the fingerprint even if its outputs happen to
agree. The existing golden scenario suite checks seeded outcomes and invariants on the real
reducer; its results are not the sole compatibility identity. A matching sampled run cannot
prove equivalence for every player choice, difficulty, seed or mod. The generator never trusts
an unchanged expected snapshot as evidence that edited code is equivalent, and does not run
expensive simulations during each build/test pre-hook.

The manifest retains a separate `sourceId` covering the original broad source/data/lockfile
inputs, plus any additional runtime dependencies. This preserves strict source matching for
co-op without letting comments, types or dev-tool updates split single-player leaderboards.

Steam leaderboard names derive from `compatibilityId`, so code that only co-op runs stays
out of it. The manifest's separate `multiplayerCompatibilityId` hashes `sourceId`,
`compatibilityId` and the mod runtime together with `src/multiplayer`, the co-op worker
and the native Steam transport. Co-op
lobbies and shared saves require it to match, so peers reject incompatible message formats
and simulation builds before joining, without moving single-player leaderboards.

When simulation behavior is introduced through registration rather than a statically reachable
import, add an explicit entry point to the generator. Changes to the digest algorithm,
presentation boundaries or input-selection policy also require a rules
revision bump. Authored references carry the scenario, seed, difficulty and this
single compatibility digest. Only current reference and invitation shapes with a
matching digest are accepted.

The manifest also includes per-file fetch integrity metadata. Browser CSV and
weather loads verify the actual response bytes, including offline-cache responses,
against the build's expected SHA-256. A mismatched response uses the existing
loading-error path instead of initializing a falsely equivalent run. Shipped text
data must use LF line endings, as enforced by `.gitattributes`; the generator
rejects CRLF data so integrity metadata remains portable across build platforms.

The manifest represents the data shipped with this build. Deployment must publish
application code and its matching `public/data` together; it must not replace
simulation data independently under an already-published build.

Competitive scoring has its own `SCORE_VERSION` (currently 2), independent of run
compatibility and app build metadata. Version 2 combines separately rounded supply
and blackout points into Service, removes investor customer points, and ranks only
completed missions. Firebase board, player-best and rank queries require both
`scoreVersion: 2` and `outcome: completed`; profile bests use `v2:<scenarioId>` keys.
Legacy score documents and profile bests remain stored, and recorded result
breakdowns retain their original category names and totals. This does not add an
old simulation runtime; continued saves run the current simulation rules.

Deploy the added `firebase/firestore.indexes.json` indexes and wait for them to
finish building before releasing the web client; deploy the matching Firestore
rules before release as well. The rules reject failed or malformed version 2
scores while allowing unversioned legacy clients to keep their historical records.
Steam leaderboard names include the score version separately from the run hash;
legacy queued scores retain version 1 board identity, while new version 2
submissions require a completed outcome. No score migration or deletion is needed.
